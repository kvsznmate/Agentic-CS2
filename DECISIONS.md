### D-041 · Resolving the MM-vs-offline tension (D-035/D-007): MM recording is sanctioned (read-only, low-risk); the AGENT stays offline for now; online play is opened only as a risk-accepted future step
**Decision:** The tension flagged in D-035 and on D-007 — training data is recorded in online matchmaking (MM) while D-007 mandates offline-only — is resolved in three parts. **(1) Recording (reading) in online MM is sanctioned.** Running capture + the raw-mouse hook + the GSI listener during live matches is READ-ONLY: it injects no input, the GSI listener is a Valve-sanctioned feature, and reading screen/input is far lower risk than injecting it (D-035 already judged this likely hasn't endangered the account). This is current practice and it stands. **(2) The AGENT still runs offline/local by default, NOW.** No change to how the agent is run today: simulated input (SendInput scan codes D-029, relative mouse D-037) goes ONLY to a local bot server. **(3) Online agent play is opened as a FUTURE direction, at explicitly accepted VAC risk — NOT a green light to inject into MM now.** D-007's offline-only rule changes from an absolute permanent bar to "offline is the operational default; running the agent online is a possible future step the user has chosen to keep open."
**The risk, recorded not waved away:** injecting simulated keyboard/mouse into a VAC-protected online match is EXACTLY what D-007 was written to avoid and can get the account PERMANENTLY, account-wide VAC-banned. That risk is unchanged by this entry. The user has chosen (2026-08) to keep online play on the table as a future option, accepting that consequence. The agent does NOT run online until a further explicit "go online now" decision is made and recorded.
**Why:** The tension was real and flagged in three places; leaving it open meant every session re-litigated it. The load-bearing distinction is READ vs INJECT: recording in MM is read-only (low risk), so sanctioning it costs nothing and matches reality; the account-ending risk is specifically INJECTING input online, which this entry does NOT authorize now. The deeper mismatch — training on MM data for an agent that (per old D-007) could only ever run offline — is removed by making online play a permitted *future* rather than a forbidden one, so the MM data isn't collected for a deployment ruled out in principle. This does NOT schedule or commit to online play; it removes the contradiction while keeping the safe default and recording the ban risk so a future session treats "run online" as a deliberate, risk-accepted step, not a casual one.
**Consequences:** D-007 is updated from "offline-only, never online MM" to "offline is the default; MM recording is read-only and sanctioned; online agent play is a risk-accepted future step, not current practice" (its ⚠ block now points here). CLAUDE.md's scope-guard line is updated to match. **The operational rule for anyone building now is unchanged: the agent runs offline against local bots.** If/when online play is actually attempted, that is its own decision with its own entry, and the permanent-VAC-ban risk above is the thing being accepted. ### D-040 · Gameplay (alive + not-freezetime) filter wired through the SEQUENCE trainer; opt-in, default OFF
**Decision:** The live-playtime filter that already existed in `data_loader.SessionDataset` / `build_datasets` (`use_gameplay_filter`, D-031/D-035) is now ALSO threaded through the SEQUENCE path the movement/radar models actually train on: `sequence_loader.build_sequence_datasets(...)` and `SequenceDataset(...)` gain a `use_gameplay_filter` parameter, and `model_lstm.train()` + its CLI gain `--gameplay-filter`. Before this, the filter stopped at the per-frame loader and the recurrent trainer had NO way to exclude dead/spectating/freezetime frames — both the FPV baseline and the `--crop radar` run trained on every frame regardless. **Default is OFF**, exactly like `--use-keep-mask`: `python -m src.model_lstm --train` still trains on all frames; alive-only training is `python -m src.model_lstm --train --gameplay-filter`. Filtering is applied at the RUN level inside `SequenceDataset` (NOT by passing the filter to the inner `SessionDataset`): the per-session keep mask combines `alive==1` AND `round_phase != 'freezetime'` (ANDed with the D-026 keep-mask if that's on too), and windows are formed only from maximal runs of CONSECUTIVE kept frames — so a window never bridges a dropped-frame gap (a pre-death frame is never stitched next to a post-respawn frame 0.5 s "later"). Files: `src/sequence_loader.py` (param on `SequenceDataset` + `build_sequence_datasets`; run-level combined-mask logic; per-filter drop counts in `_stats` + a printed summary; docstrings/invariant note), `src/model_lstm.py` (`train()` param, `--gameplay-filter`, plumbed to `build_sequence_datasets`, shown in the run banner).
**Why:** A prior-session claim that "the trainer trains only on alive frames" was checked against the code and found FALSE — the capability existed one layer below where training happens (the per-frame loader) and was never connected to the sequence trainer the models run on. This closes that gap so the intent is achievable. Run-level masking (mirroring the keep-mask, D-026) is REQUIRED for sequences: excluding frames in the inner dataset would renumber locals and hide the gaps, letting a window silently bridge a death/respawn or freezetime boundary — the exact temporal-continuity break the sequence layer exists to prevent. **Default OFF is deliberate and matches D-031/D-023:** a filter must not silently change what the #7 radar gate or the committed baseline reads just because it became available. In particular `--crop radar` (the #7 gate, D-028) must stay comparable to prior runs, and the D-027 provisional result was measured on unfiltered data — flipping the default would silently move both. So alive-only is opt-in; consistency with `--use-keep-mask` is intentional.
**Scope / interactions:** For the FPV movement baseline, `--gameplay-filter` is the right switch to train on real play only (dead/menu/freezetime frames are all-keys-released noise for a mover). For the #7 radar gate, whether the committed verdict is run filtered or unfiltered is a #7 decision (D-023/D-028) — enabling the filter there changes what the gate sees, so it must be a STATED choice, not a silent default. Only v4+/v5 sessions carry `alive`/`round_phase`; older sessions are simply not filtered (no fields), never dropped wholesale. Not a default-on change (a further explicit decision if the user wants alive-only to be the movement baseline's default, with the #7 caveat).
**Status / NOT verified on-machine:** both files are syntax-checked (py_compile clean) here; the filter's EFFECT has NOT been run on Windows against a real v5 session. Confirmation: `python -m src.model_lstm --train --gameplay-filter` on a v5 dataset should print the sequence-filter drop counts (dead/spectating + freezetime frames removed before windowing) and train on fewer windows than the unfiltered run; reported lift/MAE stay honest (eval never oversamples; the split is unchanged). Also note the current on-machine dataset is still below the D-020 volume floor, so any result stays PROVISIONAL (D-027) regardless of filtering.

### D-039 · Radar corners MASKED to black at capture (circular mask, c(67,67) r61); kills game-scene corner pixels as spurious signal
**Decision:** `grab_with_radar` now applies a circular MASK to the 128x128 radar before returning it: pixels outside a filled circle (centre (67,67), radius 61, in RADAR_OUT_HW space) are zeroed, so the stored `radar` array has BLACK CORNERS. Applied at CAPTURE, baked into every recorded frame. Geometry lives in `capture_config.RADAR_MASK_CENTER/RADIUS/ENABLED`, precomputed once as `RADAR_MASK` (an (H,W) bool) and applied as `radar[~mask] = 0`. `radar_calibrate()` applies the same mask to `radar_out.png` so the calibrate output shows exactly what gets stored. `_geom_string()` appends the mask to each file's `geom` (`..., circular mask c(67,67) r61`). Files: `src/capture_config.py` (mask constants + `_build_radar_mask` + `RADAR_MASK`), `src/capture.py` (apply in `grab_with_radar`; masked preview in `radar_calibrate`), `src/recorder.py` (`_geom_string` records the mask), `DATA_FORMAT.md` (radar array + geom + production steps).
**Why:** The square radar crop unavoidably includes GAME SCENE in its corners — the tan walls/floor visible outside the round minimap disc (clearly present in the D-038 crop). Those corner pixels CHANGE as the player moves through the map (different geometry/lighting behind the HUD), so a model could latch onto them as a spurious position signal that has nothing to do with the minimap. Forcing the corners to a constant (black) removes them as an information source: constant pixels carry zero signal, so the model can only learn from the minimap itself. This directly serves the #7 radar-signal gate — it ensures any signal the probe finds comes from the minimap, not from scene bleed. User raised the concern ("afraid the model would learn from false pixels"); it is a real train-time confound, not imaginary.
**Radius choice (r61 after real-frame check) — and an override the user should know about:** a screenshot preview at r66/r63/r60 first suggested r63 (r66 left a faint rim, r60 clipped map). The user asked for r60; I set r63 and flagged the disagreement. Then, checking a REAL stored `radar_out.png` from `--radar-calibrate`, the user spotted the CS2 radar's own yellow border RING (plus a sliver of scene) surviving along the bottom-right arc at r63 — the screenshot had been ~2px optimistic. Measuring on the real frame, r=61 cuts just inside that rim and removes it with all minimap content (walls, marker, FOV cone, labels) intact; tighter than 61 removes nothing further (residual warm pixels are in-map labels) and only risks clipping. **Committed radius is 61.** (Note: this is close to the r60 the user originally wanted; the earlier disagreement was partly a tile-label mix-up on my end — the user was pointing at the clean image, not a specific number.) Centre stays (67,67).
**Why NOT a schema bump (reversing an earlier statement in this work):** I first said this would bump v5->v6. That was wrong and inconsistent: D-038 established that a change touching only PIXEL VALUES (not shape/dtype/read-contract) is NOT a version bump, and the mask is exactly that — the array stays 128x128x3 uint8 BGR, every loader reads it identically, no reader behaves differently. Bumping for the mask but not the re-crop would contradict D-038. So `schema_version` stays 5; the mask is recorded via `geom` + this entry + DATA_FORMAT.md, the same way the re-crop was. Consequence: v5 files now come in two flavours (pre/post mask) distinguished by their `geom` — which is precisely why `geom` is per-file and the standing rule is trust-the-file's-geom.
**Where it's applied (capture vs load) — user chose capture:** I recommended a LOAD-TIME mask (non-destructive, reversible, matching D-026's principle that expensive-recording geometry calls should stay reversible), since the model's input is identical either way and a wrong radius on a baked mask costs a full re-record. The user chose capture-time (baked in) anyway; recorded as their call. The mitigation for irreversibility: the mask geometry is confirmable BEFORE recording via `python -m src.capture --radar-calibrate` (now mask-aware), and the three constants are the single adjustable point until recording starts.
**Confidence / caveats:** centre/radius were first measured from a screenshot preview (r63), then CONFIRMED and corrected to r61 against a REAL stored radar_out.png from `--radar-calibrate` (the screenshot was ~2px optimistic on the bottom-right rim). Machine/HUD-specific like the crop; re-confirm with `--radar-calibrate` if `cl_hud_radar_scale` changes. As with D-038, this cleans the radar INPUT — it does not pass #7; whether the (now scene-free) radar carries movement signal is still the empirical question #7 answers at real volume.
**Interaction with the open items from D-038:** unchanged and still standing — the pre-D-038/D-039 dataset must be re-recorded (fine, disposable), and the D-035/D-007 MM-vs-offline tension still gates the full ~20 GB re-record. The mask does not touch either.

### D-037 · Mouse OUTPUT (relative SendInput) added for navigation yaw; play_movement drives it behind a verified, opt-in gate
**Decision:** The play path can now ACTUATE the navigation-yaw look head (D-036) as real mouse motion, built as two separable pieces. **Piece 1 (`play_movement.py` load+run correctness):** the demo now loads and runs the two-output look model correctly — detects the look head from the model's list-shaped `output_shape`, finds the `move_keys` head by name (not by assumed order), unpacks `model.predict` as `[keys, look]`, loads the `*_look.look_stats.npz` sidecar, and inverts the standardization to show REAL device-unit dx/dy in the live readout. This is display-only and always on for a look model. **Piece 2 (mouse actuation):** `src/key_output.py` gains `mouse_move_relative(dx, dy)` — the project's FIRST mouse output — a `MOUSEEVENTF_MOVE` relative SendInput (the `MOUSEINPUT` struct already existed for INPUT sizing), with per-call clamping as a safety rail and (0,0) skipped; plus a `--selftest-mouse` that sweeps the view right/left/down/up so the operator can confirm the CS2 view actually turns. `play_movement.py` drives it ONLY behind `--drive-mouse`, gated three ways: the flag must be set, the model must have a look head, and the sidecar must be present (so the mouse is never driven with standardized/uncalibrated values); it is applied inside the existing `armed` block, so F9 disarm / F8 quit stop mouse output instantly. Files: `src/key_output.py` (mouse primitive + selftest + CLI), `src/play_movement.py` (look-aware load, un-standardized display, gated actuation, `--drive-mouse`). All three py_compile clean.
**Why:** D-036 left the play path expecting a single-head model; pointing it at a look model would have crashed (the old width guard read `output_shape[-1]` on a two-output list; `predict(...)[0]` mis-unpacked). Piece 1 is the necessary fix and is safe (shows dx/dy, moves nothing). Mouse OUTPUT is then required to make the look head do anything in-game — but it is a NEW actuator, and D-029 established the hard lesson that injected input to Source 2 fails SILENTLY (VK codes did nothing; only scan codes worked, and only a `--selftest` proved it reached CS2). Injected MOUSE motion is a separately-unproven path (raw-input filtering, focus, integrity may swallow it), so it gets the SAME discipline: a standalone `--selftest-mouse` that must show the view turning before any policy is trusted to it, and an explicit `--drive-mouse` opt-in that is the operator asserting they ran that check. Defaulting mouse-driving OFF (display-only) means a look model is safe to run the instant it trains, and the potentially-account-risky actuator is never silently live.
**Scope / boundary (unchanged from D-036):** this actuates NAVIGATION yaw only — the movement feed turning to traverse the map. It is NOT combat aim (still the separate detector-gated #10→#11 model via the arbiter), and mouse output here does not change that. Same offline-only rule as all actuation (D-007): `mouse_move_relative` is plain SendInput, used ONLY on a local bot server; the play loop carries the local-only warning and the arm/disarm guard. **Sign convention:** the primitive sends exactly what DATA_FORMAT.md defines (+dx right, +dy down); if the view turns the wrong way in-game, that is corrected where the model output is applied, not in `key_output`.
**Status / NOT verified on-machine (the standing bar):** everything is py_compile-clean and reasoned, but like D-029 the actuator is UNVERIFIED until run on Windows + CS2. The gate is `python -m src.key_output --selftest-mouse`: the view must visibly pan right/left/down/up. If it does NOT move while SendInput reports success, CS2 is filtering injected mouse motion and the mouse path is not usable as-is (do NOT drive the model to it) — a real possible outcome, not a formality. Only after that passes should `--drive-mouse` be used. Also note the honest caveat that even a working mouse path drives an OPEN-LOOP look model whose learnability (esp. dy) is itself provisional (D-036), so expect the usual behavioural-cloning drift; a clean actuator does not imply a good mover.

### D-036 · The movement model predicts NAVIGATION YAW (dx/dy) as a second output branch; this is navigation, NOT combat aim
**Decision:** The movement baseline (`model_lstm.py`) gains a second output head, `look`, predicting mouse motion (dx/dy) at the window's last frame, alongside the existing WASD/shift/space sigmoid head. It is **ON by default** (`predict_look=True`; `--no-look` reproduces the original WASD-only single-head baseline unchanged). The button head is byte-for-byte the same — the look head is a separate dense→linear branch off the SAME shared LSTM feature vector, so adding it cannot change what the button head computes. dx/dy targets are **standardized** using mean/std computed from the **TRAIN split only**, reused unchanged for held-out and at inference, and saved as a sidecar `.npz` next to the model (`*_look.look_stats.npz`) so play-time can invert them to real device deltas. Look is evaluated as **per-axis MAE (dx, dy) vs a zero-motion baseline**, in device units, train and held-out side by side (the dx/dy analogue of the button majority-class lift). Files touched: `src/sequence_loader.py` (additive `get_batch_with_look()` + `look_balance()`, existing `(X, Y)` button path untouched), `src/model_lstm.py` (`build_model` `n_look` branch; look standardization, training loop, eval, save-sidecar, CLI `--no-look`/`--look-loss-weight`).
**Why:** The user identified that a WASD-only agent **cannot actually move through the map** — in an FPS you steer by looking, so a mover that can't rotate the view can only strafe along the axis it spawned facing. Rotation (mouse yaw) is therefore part of NAVIGATION, not an optional extra. dx/dy come free from self-recording (D-003) exactly like the keypresses, so this is the same behavioural-cloning signal extended to the turn the player made. Standardization is because raw device deltas are unbounded and skewed (D-015: raw counts, DPI-dependent), so an MSE head needs them normalized or a few fast flicks dominate the loss; the train-only stat rule extends D-021's leak discipline to the target transform (computing stats over all data would leak the held-out distribution into the training preprocessing). The zero-motion baseline is the honest floor: "does predicting your real turn beat predicting 'don't turn'" — expected to show a clear positive on dx (horizontal yaw, the turning signal) and near-zero on dy (pitch barely moves in pure navigation), which is a true finding, not a bug.
**Scope boundary (the load-bearing part — do not let a future session misread this):** dx/dy in THIS model are **navigation yaw for the movement feed. They are NOT combat aim.** This does **not** front-run the aim gate. Combat aim remains the SEPARATE, detector-gated model (#10 detection → #11 aim), trained on enemy-present frames and conditioned on a detected enemy, which the **arbiter** switches the mouse to when the vision model sees a target (D-004: enemy seen → combat drives + movement freezes; else → navigation drives and holds its angle). The reason this is navigation and not a violation of the #10→#11 ordering: navigation look is UNCONDITIONED by design (you turn to round a corner with no enemy in frame, and that is correct), whereas aim is conditioned on detection. So predicting dx/dy for the mover is in-scope M1 movement work; it says nothing about, and does not satisfy, the detection or aim gates. A `dx/dy` output in the movement model must not later be mistaken for the aim model being done.
**Status/caveats:** whether navigation look is *learnable* from the current ~67k-frame / 4-session corpus is an empirical question the eval answers; a positive dx improvement is expected but not promised, and the same D-023/D-020 PROVISIONAL-until-real-volume framing that governs the WASD lift governs the look MAE. **Follow-up (now DONE, see D-037):** `src/play_movement.py` consumes this model to drive the agent; the added `look` output changed the model's output signature, so play-time inference had to read the `look` head and un-standardize it with the saved sidecar stats. That was completed in D-037 (Piece 1: look-aware load + un-standardized display; Piece 2: gated mouse actuation). When D-036 was first written that edit had not been made; it has since been done.

### D-035 · Training data is MATCHMAKING, not deathmatch (corrects a false premise in D-005); gameplay filter now also drops freezetime
**Decision:** Two linked things. (1) **Factual correction:** all self-recorded data to date is from **online matchmaking (MM)** matches, not deathmatch. The user confirmed this directly. Several docs stated or assumed the data was "unstructured deathmatch-style" (D-005 explicitly, PROJECT_ISSUES echoes it); that premise is FALSE and is corrected here and at D-005. (2) **Code:** the opt-in gameplay filter (`use_gameplay_filter`, D-031) now drops **freezetime** frames in addition to dead/spectating ones, so "gameplay" means own-POV alive AND `round_phase != 'freezetime'` — i.e. live playtime only. Added `load_not_freezetime_mask()` in `data_loader.py`; it ANDs into the same filter block, is reported separately (dead-count vs freezetime-count) for honesty, and only drops `freezetime` — `live`, `over`, and the `?` sentinel are kept (dropping unknowns would silently discard v4 frames where phase wasn't captured). Non-destructive, exactly like the alive filter: freezetime frames are left out of the served index, NEVER deleted from disk. Verified in isolation (a fabricated v5 session with mixed phases: filter drops the 1 dead + 2 freezetime frames, keeps the 7 live frames, served indices exactly correct).
**Why the filter is right for MM (and was NOT for the assumed deathmatch):** in real MM, freezetime is frozen-at-spawn dead time — the player cannot move, so those frames are all-keys-released noise that would worsen the already-severe WASD class imbalance (D-027: A/S/D held only 3–14% of frames; the always-release baseline is 86–97%). Dropping them is the user's goal — "train only on actual playtime." Note this is the mirror of the earlier freezetime discussion: under the (false) deathmatch premise freezetime frames might have contained real movement worth keeping; under the (true) MM premise they are genuine dead time. The correction is what makes the filter unambiguously correct.
**Why non-destructive, not a delete (the user initially asked to delete frames from disk; talked through and agreed to filter instead):** the frames the delete would remove are the very frames that make the data MM — freezetime marks round boundaries; dead frames mark round/respawn transitions. Deleting them permanently destroys the round structure, which is (a) the evidence that the data is MM at all, (b) what a future reconsideration of D-005 would need (if the data has real round timing, some enemy-location priors might be learnable rather than only hand-authored), and (c) recoverable-from only by re-recording. And the delete buys nothing the filter doesn't: the model never sees dead/freezetime frames either way, because the filter excludes them from the batch index — so deleting improves the model zero and only saves disk. Disk, if it becomes tight, is solved by archiving whole raw sessions to cold storage, not by surgically deleting frames from inside sessions. This is exactly D-026's non-destructive principle (recordings are expensive; "junk" is a threshold call that must stay reversible) applied again — and MM freezetime frames aren't even junk, they're the round skeleton.
**The unresolved tension, flagged not resolved (needs its own decision):** recording in MM sits uneasily with **D-007 (offline/local bot servers only, never online MM)**. D-007's rationale is anti-cheat risk from simulated input. Recording data in MM means running the capture + raw-mouse-hook + GSI-listener tooling during live VAC-protected matches. The GSI *listener* is a sanctioned Valve feature and reading input/screen is far lower-risk than *injecting* input (which is what D-007 is really about), so this likely hasn't endangered the account — but it is worth stating plainly that it happens. The deeper mismatch: D-007 says the *agent* can only ever run offline against bots, so we are currently training on MM data for an agent that (per D-007) can't play MM. Either the data source (MM) or the deployment rule (D-007 offline-only) will eventually have to give. That is a real decision the user must make explicitly; it is NOT resolved here, and D-007 still stands as written until it is. Recorded so the next session sees the tension rather than discovering it. **(Update: RESOLVED in D-041, 2026-08 — MM recording sanctioned as read-only/low-risk; the agent stays offline by default now; online play opened only as a risk-accepted future step, with the permanent-VAC-ban risk recorded there.)**

### D-034 · Chunk-boundary capture stalls REGRESSED (v5 ~230 ms vs D-019's verified ~80 ms); instrumented to diagnose before fixing
**Decision:** Do NOT yet change the writer or chunk size. Instead, `ChunkedSessionWriter` now records per-chunk compress+write time (`last_write_secs`) and the worst `flush()` block (`max_flush_block_s`), and `record_session` prints a three-way verdict at the end of a run: BACKPRESSURE (capture waited on the writer — the writer can't keep up), SLOW-BUT-OK (write time approaching the fill window), or WRITER-FINE / OS-WRITE-BACK (writer keeps up; any boundary gap is the OS flushing the chunk's dirty pages). No functional change to the write path, format, or crash-safety.
**Why:** On-machine, a v5 session (`session_20260820_103332`, 15,766 frames, 9 chunks, ~163 MB/chunk) showed chunk-boundary inter-frame gaps of **~210–242 ms at 7 of 8 boundaries** — `inspect_recording`'s heuristic flagged "synchronous flush blocking the loop." That heuristic is stale: D-019 already moved the write to a background thread AND **verified on-machine** that boundaries dropped to **69–82 ms** (from the pre-thread 10,657 ms). So this is a genuine REGRESSION against a known-good baseline, not the old synchronous-flush bug. Two things grew the per-chunk buffer since D-019 was verified: D-024's radar array (+~49 KB/frame) and D-031/D-033's GSI arrays; a v5 chunk is ~306 MB uncompressed vs v2's ~180 MB, so both the writer's compress cost and the OS write-back volume per boundary went up. **Crucially, the mechanism matters because the fixes diverge:** backpressure (writer slower than the ~138 s fill window) would stall capture at the boundary and is fixed by a SMALLER chunk or a deeper queue; OS write-back (Windows flushing ~163 MB of dirty pages, stalling the whole process including the capture thread) is a different problem. The capacity-1 queue means only backpressure can make `flush()` block — so timing the block distinguishes them cleanly. D-025's standing lesson ("a tool that can mislead must fail loudly; measure, don't guess") applies directly: rather than assume and re-tune blindly, the writer now reports which mechanism it is. **Also flagged:** `inspect_recording`'s boundary DIAGNOSIS text still says "synchronous flush" and is now misleading post-D-019 — left for a follow-up, but noted here so its verdict isn't taken at face value. **Severity/scope:** not data-corrupting (chunks are atomic; the session loads fine) and not blocking the v5 capture itself; it dents the realised FPS (this session ran ~12.9 vs the ~15 bar, D-016) and reintroduces a corrupted mouse-delta at each boundary (dx/dy summed across the ~230 ms gap), which matters for the ~20 GB dataset (D-020) about to be recorded. Next step: one `--record` run reads out the new writer diagnostics; the committed fix (smaller CHUNK_FRAMES, deeper queue, or accepting write-back) is chosen from that number, and recorded as its own decision.

### D-032 · Own-POV / spectating is detected by the STEAMID MATCH, not `observer_slot` (corrects the D-031 alive rule)
**Decision:** The alive rule's spectating guard is changed from "`observer_slot` absent" to "**`player.steamid == provider.steamid`**". `extract_state()` in `src/gsi_listener.py` now computes `own_pov = (player.steamid == provider.steamid)` (falling back to `own_pov=True` only if a steamid is missing), sets `spectating = not own_pov`, and defines **`alive = own_pov AND health > 0`**. `observer_slot` is downgraded to an informational field, no longer part of any decision. The probe's readout (`gsi_probe.py`) was updated to match: it now flags death on the ALIVE transition (catching the alive→spectate path, not just health→0) and reports spectating via the steamid mismatch. No format change; v4 stands.
**Why:** The D-031 rule assumed `observer_slot` only appears when spectating (the CSGO-doc reading). On this CS2 build that is FALSE, proven by the user's own captured payloads: in an alive, `activity:"playing"`, own-team payload with `health:100`, `observer_slot:5` is present — it is the player's OWN slot index. So "observer_slot absent" was never true in-game, and the rule forced **every in-game frame to `alive=False`**. This surfaced immediately on the first `--verify-gsi` run: the readout showed `alive=False` while the user was plainly alive, and went quiet on death (GSI stops POSTing on-change and the change-only readout had nothing new to print — not a crash). **The correct tell, also proven from the same log:** when the user died and the camera moved to a living teammate, `player.steamid` changed to the observed player's id and no longer matched `provider.steamid` (which is always our account); that was the ONE frame in the session where the ids differed, and it is exactly the spectating frame. Replaying the corrected rule over all 110 logged payloads gives the right labels end-to-end: alive throughout play, dead on the health-0 death frame (n=89), dead on the single spectate frame (n=90, health 100 but foreign steamid), alive again on respawn (n=91). `activity` alone was rejected as the tell because it stays `"playing"` while spectating a teammate (n=90), so it does not distinguish the two; the steamid match does. **Caveat honestly noted:** the user's death was brief, so only ONE spectate frame was captured — enough to prove the mechanism (foreign steamid → dead) but not a long spectate sequence; the real confirmation is a live `--verify-gsi` re-run and a recorded session where a longer dead/spectate period is checked. **Consequence:** this is a parsing correctness fix, not a design change — D-031's architecture (shared listener, per-frame sample, forward-fill, liveness gate, v4 fields, opt-in loader filter) is unchanged; only the interior of the alive predicate is corrected. It also means D-030's "feasibility CONFIRMED" was over-read: health/death worked, but the playing-vs-spectating distinction was NOT actually validated then (the harness had `spectating` pinned true the whole time and nobody checked), which is why on-machine verification of the built path — not just feasibility — remains the bar (issue #21).

### D-031 · GSI alive/gameplay state folded into recording via a shared listener; format bumped v3 -> v4 (`alive` + `round_phase` per frame)
**Decision:** The GSI feasibility harness (D-030) is now WIRED INTO RECORDING. Four code files changed together, plus DATA_FORMAT.md. (1) **`src/gsi_listener.py` (new, shared):** a `GsiListener` class owning a background `ThreadingHTTPServer` that receives CS2's GSI POSTs and exposes the LATEST parsed self-state through a narrow, lock-protected slot — `read_latest() -> (state|None, age_seconds|None)` (non-blocking snapshot), `wait_for_first_update(timeout)` (the liveness gate), `start/stop/__enter__/__exit__`, optional `on_update` callback. The alive RULE and payload parsing (`extract_state`) live here so there is ONE definition of "receive + parse GSI." (2) **`src/gsi_probe.py` (rewritten):** now a thin feasibility HARNESS over the shared listener (change-printing, cadence stats, JSONL logging via the callback) — the duplicated HTTP server + `_extract` are gone; operator behaviour unchanged. (3) **`src/recorder.py`:** `SCHEMA_VERSION = 4`; `Recorder(use_gsi=...)` owns/starts/stops the listener and samples it ONCE per frame in `read_frame_record()` via `_sample_gsi() -> (alive: bool, round_phase: str)`; `ChunkedSessionWriter` buffers + writes two new per-frame arrays (`alive` uint8, `round_phase` `<U16`); `record_session(require_gsi=True, gsi_grace=15s)` runs the liveness gate; new `verify_gsi()` + `--verify-gsi` CLI. (4) **`src/data_loader.py`:** reads v4 (`alive`/`round_phase` added to `_PER_FRAME_OPTIONAL`, `_SUPPORTED_SCHEMA` += 4); new `load_alive_mask()`; `SessionDataset`/`build_datasets` gained opt-in `use_gameplay_filter` (default OFF) + a `--gameplay-filter` CLI flag. DATA_FORMAT.md is authoritative for the v4 schema.
**The alive rule (load-bearing):** *[CORRECTED by D-032 — the spectating guard is the steamid match, not `observer_slot`; the description below is the original, superseded reasoning, kept for the record.]* `alive == 1` iff the payload has a LOCAL `player.state.health > 0` **AND** it is NOT an observer/spectator payload (no `player.observer_slot`). The own-POV requirement is the critical part: when you die and spectate a living teammate, GSI's `player` block describes the OBSERVED player (health > 0), so a naive `health > 0` would label those frames ALIVE — poisoning the dataset with someone else's screen paired with our idle/dead inputs. Requiring own-POV makes spectating read DEAD. A parsed alive of `None` (no local health in that payload — pure menu/observer) is treated as dead by the recorder. **`round_phase`** is the coarse `round.phase` (freezetime/live/over) or the sentinel `"?"`; only the coarse phase is available from solo play (exact countdown is observer-only, D-030) — a constraint carried forward to M5.
**Why a shared listener, threaded, sampled once per frame:** GSI is push-based, throttled (0.1s/on-change, 10s heartbeat), event-driven HTTP; the capture loop is deliberately a single synchronous loop (D-015 "way one") whose correctness is the whole M0 gate. So the listener follows the EXACT pattern `raw_mouse.RawMouseListener` already uses: a producer on its own thread, and the loop samples a narrow lock-protected slot once per frame. The GSI thread touches NOTHING the capture loop owns — same threading-confined-to-I/O reasoning that made D-019 (threaded chunk writes) safe. The per-frame sample is one non-blocking slot read, so it cannot stall the loop; the frame/input sync path stays fully synchronous. This is why the shared-module option was chosen over importing the probe's server into the recorder (the user left the choice to "whichever keeps the sync path safest"): a narrow `GsiListener` interface is the safe boundary; dragging the probe's print/log harness onto the critical path is not.
**Forward-fill is inherent, and the alive representation is a bare boolean (user's decision):** because GSI updates arrive coarser (~100ms+) than the frame interval (~67ms), MOST frames have no fresh GSI update, so `read_latest()` returns the last state — forward-filling for free via the slot. The user explicitly rejected an `unknown`/`gsi_age` representation and a three-state {alive/dead/unknown}: the on-disk field is a plain 0/1, "alive or dead till the next update from the reader." **Known limitation, accepted not missed:** a bare boolean freezes the "GSI dead vs just quiet" question — a crashed/quiet GSI would keep writing its last value onto every frame. Backstops (all already in place): the startup liveness gate below, `review_session.py` (eyeball a session), and the D-026 keep-mask as a secondary variance-based hygiene layer. Recorded here so a future session sees this was a deliberate trade, not an oversight.
**Liveness gate + "drop pre-GSI frames" (user's first-contact choice, hardened):** the user chose to DROP frames before GSI's first POST rather than default them to dead. Implemented as: `record_session` waits for the first GSI POST BEFORE creating the session folder or grabbing any frame; only then does the capture loop start. Consequence: there are NO pre-contact frames to drop (recording simply doesn't begin until GSI is live), so every recorded frame carries a real alive value AND there is no forward-fill hole at the top. The gate also closes a catastrophic failure mode the naive "drop pre-GSI" has: if GSI never connects (the many silent failures in `gsi/README.md` — cfg saved with a BOM, wrong cfg dir, CS2 not restarted, port blocked), a naive drop yields a silent ZERO-FRAME session after an hour of play. Instead, on `require_gsi=True` (default) the recorder REFUSES to start after `gsi_grace` (15s) with the setup checklist — a loud early failure, the same D-025 lesson ("a tool that can mislead must fail loudly") applied to recording. `require_gsi=False` is an escape hatch (records anyway, leading frames marked dead). `writer` is guarded as `None` through the gate so an aborted start finalizes nothing.
**Loader gameplay filter (opt-in, ANDed with D-026):** `use_gameplay_filter=True` serves only frames whose stored `alive` flag is 1, by leaving non-alive frames out of the global index — the SAME structural exclusion the D-021 split and the D-026 keep-mask already use (a dropped frame is simply not indexed). It is the AUTHORITATIVE gameplay filter; the D-026 radar-variance keep-mask is now the secondary heuristic. When both are on, a frame must pass BOTH (logical AND) — they are complementary (alive catches menu/dead/spectate that the radar can't; variance catches blank radar the flag might miss). BOTH default OFF, so the #7 gate and the committed split never move because a filter or a v4 recording appeared. v1/v2/v3 sessions (no `alive` field) are simply not gameplay-filtered rather than dropped.
**Dataset consequence:** the mid-recording v3 dataset (a couple of sessions) is deleted and re-recorded fresh as v4 (user's call), so there is no mixed-format dataset to manage. **Verified in isolation here** (py_compile clean on all four files; a round-trip test confirmed the `round_phase` `<U16` npz store and the alive-rule truth table including spectating-living-teammate -> dead). **NOT yet run on-machine** (needs Windows + CS2): `python -m src.recorder --verify-gsi` (confirm alive tracks life/death + spectating -> dead), then a short `--record` producing a v4 session, then `inspect_recording` + a loader `--gameplay-filter` frame-count check. `inspect_recording.py` was NOT updated for v4 and may need a look if it asserts on schema version. This entry is the built realisation of D-030's "explicitly NOT done yet" steps (a) and (b).

### D-029 · Simulated key output uses SendInput SCAN CODES, and is offline-only (first actuation component)

### D-027 · First model is a WASD-from-FPV recurrent baseline (movement-only, many-to-one LSTM)
**Decision:** The project's first trained model is a **behavioural-cloning baseline that predicts WASD from a short FPV sequence** — a CNN encoder (TimeDistributed, shared across time) feeding an **LSTM** that returns its final state to **4 independent sigmoids** (w/a/s/d), **many-to-one**, sequence length **T=8** (~0.5 s at 15 FPS), loss = per-key **binary cross-entropy**. Built in **tf.keras on TF 2.10** (environment.yml / D-011 — the pinned stack and the reference study's framework). WASD is modelled as 4 INDEPENDENT binary outputs, NOT a 4-way softmax, because W+D etc. are held simultaneously (diagonal movement) — a softmax would forbid diagonals. Two files added: `src/sequence_loader.py` (sliding-window sequences over the existing loader) and `src/model_lstm.py` (model + trainer + honest eval). The trainer takes `--crop`, so the SAME script trains the FPV baseline (`full`/`centre`) AND runs the #7 movement-from-radar comparison (`radar`) — see D-028.
**Why:** Movement/aim is the one thing trainable RIGHT NOW with zero new labels — the recorded keypresses ARE the labels (D-003), no annotation, no gate in the way (unlike detection #10 / the arbiter #16, which sit behind Gate 3 and a labelling sub-project). Movement-only is the tightest such baseline and answers the project's central question — does a model learn to act from OUR pixels and OUR actions — with the fewest moving parts. Recurrent (not single-frame) was the user's choice and matches the study's design: movement is temporal (momentum, counter-strafing) and a single frame can't see it; many-to-one keeps the head simple. T=8 is a deliberate default (~0.5 s), tunable via `--seq-len`. **Sequence batching is a new layer, not a loader change:** `sequence_loader.py` reuses `SessionDataset` for all decoding/cropping/radar/action-assembly and only adds a windowing index, so there is no second code path that could drift from DATA_FORMAT.md. It enforces two invariants, both unit-tested (`test_seq_logic.py`, run in dev): (1) a window NEVER spans a session boundary (D-021 — cross-session frames aren't temporally continuous); (2) with the keep-mask (D-026), a window is only drawn from a RUN of consecutive kept frames and NEVER bridges a dropped-frame gap (a pre-menu and post-menu frame must not be called 0.5 s apart). Runs shorter than T contribute nothing. **The honest metric:** WASD is imbalanced (W dominates), so raw accuracy is a trap — an "always-W" model scores high while learning nothing. The trainer reports, per key, held-out accuracy vs the majority-class baseline and the LIFT between them, next to the TRAIN lift (a large train/held-out gap is the visible fingerprint of memorisation). Same baseline-lift discipline as `radar_probe.py`. **Data-volume honesty (D-023 applied to modelling):** at the current ~15k frames / 15 sessions an LSTM overfits fast, so a good number could be memorisation. The trainer stamps the result **PROVISIONAL** below a volume floor (`MIN_TRAIN_WINDOWS`, `MIN_SESSIONS`) and refuses to let a shiny lift pose as a committed baseline; the deliverable NOW is a working, honest train+eval pipeline, the committed benchmark comes at D-020 volume. **Status / RAN ON-MACHINE (2026-08-19):** the FPV baseline trained successfully on the RTX 4050 (TF 2.10 GPU). First result is a **PROVISIONAL SMOKE-TEST PASS**: 11,144 train / 4,219 held-out windows (below the 15k floor, correctly flagged provisional). **The model learns generalisable signal and does NOT overfit** — held-out mean WASD lift +6.6pp vs train +7.0pp, a 0.4pp gap. But the mean hides the real story, which is per-key: **W held-out +23.5pp (strong, real), A +0.5pp / S +0.9pp / D +1.5pp (essentially flat).** So the model learned FORWARD movement well and strafing/retreat barely — expected, because A/S/D are rare (held 14%/3%/10% of frames) and heavily imbalanced (the always-release baseline is 86–97%), and strafe/back are less visually determined than forward. This is a genuine finding about WHAT is learnable from the FPV, not a bug. Confirms the pipeline is sound; the committed baseline still needs D-020 volume, and the flat rare keys are the open question (more data vs class-weighting vs accepting they're weak). Windowing logic was unit-tested pre-run (`test_seq_logic.py`). Note: ~15 min for 10 epochs (mss/CPU-bound + GPU memory spill on the 4050's ~3.4 GB — non-fatal, TF falls back); the `ptxas.exe`-missing warnings are also non-fatal (driver does PTX compilation). Preprocessing (/255) is a Rescaling layer INSIDE the model so inference matches training and the loader stays uint8 BGR (no BGR→RGB introduced — consistency over convention).

### D-026 · Dataset hygiene is a sidecar keep-mask, not a filtered copy or destructive edit
**Decision:** Blank/no-radar frames (buy menu, halftime, dead/spectate screen) are removed from training by a NON-DESTRUCTIVE **sidecar keep-mask**, not by deleting frames or writing a second "clean" copy of the session. `src/clean_session.py` computes per-frame radar variance (reusing `radar_probe._radar_variance` + `_gameplay_threshold` — ONE definition of "blank," shared with the probe, no second detector), derives the blank/present cut ONCE from the pooled variance histogram across all sessions (Otsu, with a bimodality guard: it refuses to write masks on a non-bimodal distribution unless `--force`), and writes `keep_mask.npz` (`keep` bool (N,), plus the per-frame `variance` and the `threshold` so the cut can be re-applied without recomputing) + `clean_report.json` into each session folder. Recordings are never modified. The loader reads the mask only on OPT-IN: `build_datasets(use_keep_mask=True)` / `SessionDataset(use_keep_mask=True)` exclude masked frames by leaving them out of the global index (the same structural exclusion the D-021 split uses — a dropped frame is simply not indexed); **default is OFF** so the #7 gate and the committed split do not change because a mask appeared on disk. `src/review_session.py` is a scrubber (FPV + radar side by side, seekbar, per-frame action readout) that tints mask-dropped frames so the cut can be verified by eye. Files added: `clean_session.py`, `review_session.py`; `data_loader.py` gained `load_keep_mask` + the opt-in `use_keep_mask` path.
**Why:** Continuous recording through a match (D-018) is correct — restarting CS2 every round to avoid dead-screen/menu frames is exactly the babysitting #4 forbids — so the junk-frame problem moves downstream to cleaning. Sidecar mask over filtered copy because: (1) recordings are expensive and D-018's crash-safety exists precisely so we don't lose them — a deleting cleaner works against that; (2) "blank" is a *heuristic with a threshold*, so it must stay reversible and re-runnable (regenerate in seconds if the cut is revised) rather than baked into a duplicate; (3) a filtered copy would store the ~9 GB/hour dataset TWICE (DATA_FORMAT.md budget) to encode one threshold decision the mask gives for free; (4) the mask extends patterns already in the loader — the split already excludes crashed sessions (D-022) by omission from discovery, so "skip masked frames" is the same shape, not a new mechanism. Default-off is deliberate: the radar probe (#7) has its own opt-in `--filter-blank` and reads all frames by default; silently changing what the loader serves because a sidecar appeared would move the #7 gate's data under it. **Measured before building:** `radar_probe --gameplay-report` on the current data showed a cleanly BIMODAL variance distribution (15,011 of 15,468 frames in the top variance bin; Otsu cut at variance≈132; a near-empty gap between the modes), confirming variance actually separates blank from present here — so the detector rests on a checked premise, not an assumption. **Known limit (why the review tool ships alongside, not after):** the cut is on RADAR variance, so it only catches frames where the *radar* is blank. A frame can have a normal radar and still be junk — the buy menu overlays the FPV while the minimap still renders behind it, so a buy-menu frame can pass the variance cut as "gameplay." "Blank radar" ≠ "not useful." Catching menu-open-but-radar-present junk needs an FPV-side signal, not variance; that is deliberately NOT built yet — `review_session.py` is how we look for whether that class of junk is even present in the data before deciding it's worth a second detector. **Status / not yet run on-machine:** the mask write path, the loader's opt-in exclusion, and the scrubber are reasoned + syntax-checked but unexercised here; confirmation steps are `python -m src.clean_session --report` (see the pooled cut), `--all` (write masks), `python -m src.review_session` (eyeball what's dropped, and hunt for menu-with-radar junk), then a loader `build_datasets(use_keep_mask=True)` frame-count check. The ~1.9% blank rate the report predicts means the mask is hygiene, not a dataset rescue — the review tool's real job here is turning "I can only see screenshots" into "I can watch the session" and exposing any junk variance can't catch.

### D-025 · The #7 radar probe fits on 32x32 grayscale features (+ solver made numerically honest)
**Decision:** `src/radar_probe.py`'s signal probe DOWNSAMPLES the stored 128x128x3 radar to **32x32 grayscale (`PROBE_SIZE=32`, ~1,024 dims)** before fitting its per-key logistic probe — it no longer fits on the full 49,152-dim flattened radar. The hand-rolled numpy solver was also made numerically robust: a **sign-stable sigmoid** (no `exp` overflow), **lr 0.5→0.05** with **iters=400** and **gradient-norm clipping**, a **variance floor** (`sd≥1e-2` after /255) so near-constant background pixels can't explode under standardisation, **stronger L2 (5.0)**, **float32** working arrays, a **loss print every ~50 iters**, and a **divergence guard** that makes the probe print `VERDICT: NO RESULT` and REFUSE per-key numbers if the fit's loss goes non-finite or increases. The group-split, the PROVISIONAL data-volume gate (D-023), and the verdict logic are unchanged. This does NOT change the stored data (still 128x128x3, D-024) — only what the probe feeds its linear model.
**Why:** Two failures on the first real runs, same file. (1) **Divergence:** the initial fit overflowed `exp` and produced anti-correlated accuracies (a key held 7% of the time "predicted" at 22% — a −70pp mean lift). That is the fingerprint of a diverged optimizer, NOT a signal-free radar; a working probe on genuinely signal-free data sits at ~0 lift, not deeply negative. `lr=0.5` on ~49k correlated pixel dims was the cause. (2) **Cost:** even after the numerics fix, fitting on 49,152 float64 features over thousands of frames for 400 iterations is a multi-TFLOP, multi-GB grind on this machine's non-SIMD numpy — it ran **>20 minutes with no output** and had to be killed, because the fit was also silent. The 32x32-grayscale reduction (~48x fewer dims) makes the fit finish in seconds, and the loss print makes "working" visibly distinct from "stuck". **Why 32x32 grayscale is legitimate, not just a speed hack:** a linear probe answers only "is there ANY linearly-decodable position→movement signal in the radar." Reading *which blob is where* on a minimap survives a 32x32 grayscale reduction; colour and full resolution are not what a linear model can exploit anyway. If signal can't show at 32x32, 49k noisy dims would not have rescued a *linear* probe — and the escape hatch for that case is already the documented one (try a small CNN before any KILL, per D-023/#7), which would consume the full-res radar directly. So the downsample changes what the *probe* sees, not what the *models* will later see. **Consequence:** this only affects the #7 gate tool; nothing downstream reads these probe features. The probe still cannot produce a committed verdict below the D-023 floor (still true at the current ~3 sessions / ~7.5k frames — under both floors), so this fix is about making the tool SOUND and FAST for when real v3 volume exists, not about extracting a verdict now. **Lesson (third instance this project, recorded so it sticks):** a tool that can mislead must fail loudly — the inspector misreported v3 as v2, the probe's first solver printed confident garbage, and the probe's second version was a silent 20-minute black box. Each fix was the same shape: make the tool narrate what it's doing and refuse to emit numbers it can't stand behind.

### D-024 · Two-resolution capture: a separate high-res radar crop alongside the FPV (format -> v3)
**Decision:** Capture now produces TWO feeds from ONE grab. The FPV stays 150x270 (D-012, unchanged). In addition, a SEPARATE high-resolution **radar** crop is taken from the FULL 1920x1080 grab BEFORE the FPV downscale, cropped to the minimap source rectangle (measured `L=10, T=10, W=260, H=260`, a square tight on the minimap disc) and resized to **128x128** (square → no distortion). Both come from `Capture.grab_with_radar()`, so they share the tick's single capture timestamp and cannot drift. On-disk format bumps **v2 -> v3**: each frame stores a new per-frame `radar` array (N,128,128,3 uint8 BGR) index-aligned alongside `frames`; DATA_FORMAT.md is authoritative. The loader serves the radar from this stored array via input `"radar"` (NOT a crop of the FPV); the old FPV-crop `RADAR_CROP_DEFAULT` is RETIRED. Five files changed together so they agree: `capture_config.py` (radar rectangle constants), `capture.py` (`grab_with_radar`), `recorder.py` (writes v3 with radar; `record_session`), `data_loader.py` (reads v3, serves stored radar, `_SUPPORTED_SCHEMA` += 3), `DATA_FORMAT.md` (v3 schema). The radar geometry is baked into every recorded file at capture time and is machine-specific — files self-describe it in `geom`.
**Why:** At the 150x270 FPV downscale the radar corner is too low-res to read self-position (the #7 finding). Morphology/upscaling cannot recover detail the downscale destroyed — the information isn't in those pixels. The two feeds have genuinely different resolution needs: 150x270 is fine for the FPV (the study used ~that), but the minimap needs its own resolution. Two options were weighed: (A) raise the whole model input resolution, or (B) a separate high-res radar crop. **B was chosen** because it keeps the permanent inference-time cost low — the FPV path is unchanged, so the detection/aim models and the two-model arbiter loop pay nothing extra; only a cheap crop+resize is added to a grab we already do. (A) would inflate every frame's storage AND raise both models' inference cost forever on the exact hot path D-016 says is the bottleneck, to buy FPV resolution we don't need. The load-bearing assumption — that the radar is legible when cropped from the full-res grab — was MEASURED before committing (`--radar-calibrate`; uploaded `radar_out.png` showed a legible minimap, position/geometry/dots readable at 128x128), because the rectangle is frozen into every recorded file and a wrong call would mean re-recording everything. The box was then tightened off a labelled pixel grid to drop the dead HUD surround (border + empty bottom strip carry no movement signal). **Cost accepted:** +~49 KB/frame (128x128x3) on top of the FPV's ~121 KB (~+40% before compression), which reshapes the D-020 storage math (~20 GB buys proportionally less playtime); kept 128x128 as the legible-but-lean size. **Partially supersedes D-017 / D-012's "store ONE full frame, defer all crops to the loader" stance:** the radar is now a distinct captured array, not a loader-side crop, because the needed resolution only exists before the FPV downscale — it cannot be recovered later, so it must be captured, not deferred. The FPV half of that stance is unchanged. **Consequence for existing data:** the ~30 min already recorded is v2 (FPV only, no radar array); the loader stays back-compatible (reads v1/v2, radar unavailable for them), but those sessions cannot serve the #7 radar probe and will be re-recorded — an acceptable cost against the not-yet-hit ~20 GB target (D-020). **Not yet run on-machine:** the v3 write path and the loader's radar read are reasoned but unexercised here; a fresh `--record` + `inspect_recording` + a loader `--crop radar` check are the confirmation steps, and `--profile` measures the radar crop's added per-frame cost against the ≥15 FPS bar (D-016).

### D-023 · The #7 radar gate emits a PROVISIONAL verdict below a data-volume floor
**Decision:** `src/radar_probe.py` (the M2 gate tool) prints its WASD-signal verdict as **PROVISIONAL** whenever it runs on fewer than `MIN_PROBE_FRAMES` (20000, ~22 min at 15 FPS) or `MIN_PROBE_SESSIONS` (3). A provisional result is a smoke test and MUST NOT be recorded here as the committed M2 gate outcome; the committed verdict + the M2 threshold are set only from a re-run at full data volume (D-020). The probe evaluates on a **whole-session** train/test split (D-021 style), never per-frame. A linear probe is treated as a floor: a committed "no clear signal" warrants one CNN probe before the KILL flag; a committed clear positive is a real GO.
**Why:** #7 is a go/no-go that gates all of M5 (the hand-authored navigation panel and controller). A behavioural-cloning probe on a small, highly-correlated sample can read "signal" from very little — so a PASS computed on ~30 min of data is not trustworthy, and recording it as the gate result would send us building M5 on a foundation that was never really tested (the exact papered-over-gate failure the derisking discipline forbids). The per-frame-leak risk is the same one D-021 addresses for training; here it would also fabricate a false PASS, hence the group split inside the probe too. The floor makes the tool honest about its own inputs: build and run it now for a smoke test (promising-vs-yellow-flag), but earn the committed verdict at real volume. Thresholds are floors for the verdict to *mean* something, not performance targets — deliberately set, not tuned. **Method note recorded in #7:** unlike the reference study, we cannot get ground-truth position from memory (RAM offsets dead on Source 2, D-002; the study's `localpos` came from memory, not pixels), so recovering navigation signal from the radar *pixels* is a genuinely new problem for us and a gate that can really fail.

### D-022 · Crashed/incomplete sessions are excluded at discovery, not just refused at load
**Decision:** `data_loader.discover_sessions()` EXCLUDES any v2 session folder whose `manifest.json` has `complete: false`, lists no chunks, or is unreadable — so an interrupted recording never enters the split. The rule lives in `_session_usability()`; skipped sessions are reported (`discover_sessions(report=True)`, `list_skipped_sessions()`, and the `data_loader` CLI) so a crashed session is visible, not silently dropped. A v1 bare `.npz` has no manifest/flag and is assumed complete. Locked by `test_crashed_session_excluded_from_discovery` and `test_crashed_session_never_in_split`.
**Why:** Surfaced for real: `session_20260810_151611` crashed mid-write, leaving `complete:false` + `chunks:[]` + a stray `chunk_00000.tmp.npz` (the D-018/D-019 crash-safety design behaving correctly — the manifest refused to claim un-finalized frames). But the loader still *discovered* that folder, hashed it into the split (D-021), and it landed in held-out — producing a **0-frame held-out set**, i.e. no test set at all for #7/#10. Refusing it only at load wasn't enough, because the split is decided from the discovered *names* before any frame loads; an empty session has to be filtered at discovery or it becomes a phantom split member. This is the mid-session-crash case #4 consciously waived testing — it happened in the wild, contained cleanly, and this closes the one real gap it exposed (the loader trusting a crashed folder). The crashed session's ~167 MB were deemed not worth recovering against the ~20 GB target (D-020) and deleted.

### D-021 · Held-out split is by WHOLE SESSION, deterministic by name-hash (~20%)
**Decision:** The train/held-out split (#6) is reserved **by whole session, never by frame**, and assignment is a **deterministic hash of the session name**: a session is held-out iff `blake2b(name) mod 1000 < holdout_frac*1000`, default `holdout_frac=0.20`. Implemented in `src/data_loader.py` (`is_holdout`, `split_sessions`, `build_datasets`), which builds train and held-out as two datasets over **disjoint** session lists so held-out frames are physically absent from the training iterator (leak-free structurally, not by a flag someone can forget). A `manual_holdout=` override lets a caller name held-out sessions explicitly during the tiny-data phase, but it is an override — the committed default is the hash.
**Why:** Frames within one session are consecutive ticks of the same continuous motion and are therefore highly correlated; a random **per-frame** split would put near-duplicate frames in both train and held-out and silently inflate every downstream metric — the #7 radar probe, the #10 detector, the #11 aim head. Splitting whole sessions removes that leak. **Hash-by-name** (over a shuffle+seed or a stored split file) makes the split a pure function of the session names present: reproducible across machines/runs with no stored state, and — critically — **adding new sessions never reshuffles existing ones** (asserted in `test_data_loader.py`), so recording more data never disturbs the reserved set. `blake2b` not Python `hash()` because the latter is salted per-process and would not be stable. **Honest caveat:** at small session counts a 20% hash split can land 0 or 2 sessions in held-out by luck — the guarantee is *reproducible + leak-free*, not *exactly 20% right now*; the fraction converges as sessions accumulate. This satisfies the "held-out split reserved" half of #6's acceptance, and reserves it BEFORE the data is used so #7/#10 stay honest gates.

### D-019 · Chunk writing moved to a background thread (fixes the per-chunk capture stall)
**Decision:** `ChunkedSessionWriter` writes chunks on a **single background writer thread** (Option A: capacity-1 handoff queue). `flush()` snapshots the current buffer, assigns its index/filename, enqueues it, and immediately starts a fresh buffer so the capture loop keeps running; the worker compresses + atomically writes (`.tmp.npz` -> `os.replace`) and updates the manifest off the hot path. This supersedes the synchronous flush in D-018 (format and crash-safety unchanged; only *where* the write runs changed).
**Why:** On-machine, `inspect_recording` localised a **10,657 ms capture stall at exactly the frame-1800 chunk boundary** — 1 of 1 boundaries stalled, 100% of large gaps at boundaries — proving the synchronous flush froze the capture loop for ~10 s while writing ~180 MB. Over a long session that's a hole every ~2 min *and* a corrupted mouse-delta at each boundary (dx/dy summed across the 10 s gap). Unacceptable for the extended recording M1 needs; it's a flaw introduced by D-018's inline write. Threading the write removes the stall: capture never pauses to save.
**Why this does NOT violate D-015's "single synchronous loop":** that decision exists to *prove frame/input alignment*, and the alignment path stays fully synchronous — the writer thread touches ONLY finished, handed-off buffers, never the capture, timestamps, or mouse listener. Threading is confined to disk I/O, which has nothing to do with sync. So "way one" for capture stands; this is I/O offload, a different and safe use of threads. **Option A (single-chunk depth) over a full queue:** the queue holds one chunk; if the writer were still busy when the next chunk is ready, `flush()` blocks (bounding memory to ~2 chunks). With a ~10 s write vs a ~120 s fill window (12x headroom) this effectively never triggers, but if the disk ever stalled that long we'd rather pause than grow memory unbounded — matches "don't over-engineer": a full unbounded queue buys nothing at this margin. Writer errors are captured and surfaced; on any write failure the session is marked **incomplete** (readable up to the last good chunk) rather than falsely complete. **Verified on-machine (2026-08):** a fresh 5-min `--record` (3862 frames, 3 chunks) + `inspect_recording` confirmed the boundary stall is GONE — gaps at frames 1800 and 3600 are 82 ms and 69 ms (were 10,657 ms), slowest gap in the whole session 127 ms, jitter down to 5.3 ms from 176 ms, clean exit with the writer thread joining properly. The threaded write did its job.

### D-018 · Extended sessions are chunked folders (crash-safe, bounded memory); format bumped to v2
**Decision:** Long recordings are written as a **session folder of chunk files** (Issue #4), not one giant `.npz`. `recorder.py --record` now calls `record_session()`, which flushes a `chunk_NNNNN.npz` every `CHUNK_FRAMES` (1800, ~2 min at 15 FPS) via `ChunkedSessionWriter`, frees that RAM, and maintains a `manifest.json`. DATA_FORMAT.md bumped **v1 -> v2**; the per-frame array schema inside each chunk is byte-for-byte v1, so only the container changed and v1 single files stay readable. `--record-single` keeps the old one-file writer for the short round-trip check; `inspect_recording.py` reads both.
**Why:** The v1 `record()` accumulated every frame in a Python list and wrote once at the end — two fatal flaws for the extended sessions #4 requires: (1) memory grows unbounded (~1.8 MB/s of raw frames), so a long session eventually exhausts RAM and crashes; (2) a crash at any point loses the ENTIRE session, because nothing is on disk until the loop finishes. Chunking fixes both: only one chunk is in RAM at a time (bounded memory), and a crash loses at most the current in-progress chunk (crash-safety). Crash-safety is implemented concretely: each chunk and the manifest are written to `.tmp` then atomically `os.replace`d, so an interruption never leaves a half-written file masquerading as complete — loaders ignore stray `.tmp`; and `record_session` flushes + finalizes in a `finally` block, so F8, timeout, Ctrl-C, or an exception all still close the session cleanly with the manifest marked `complete`. Disk safety: refuses to start below `MIN_FREE_DISK_GB` (5) and stops cleanly if free space crosses that floor mid-session, so an unattended run can't fill the drive. **Chunk size** (1800 frames) trades crash-loss granularity against file count: ~2 min lost worst-case, ~30 chunks/hour — both reasonable. **Not yet run on-machine:** the crash-safety and disk paths are reasoned, not yet exercised; a pilot `--record` (and the size-target it sets) is the remaining #4 step. Value not yet locked: the dataset size target (hours/frames) is committed AFTER the pilot, per the #4 spec.

### D-017 · Data format v1 locked: full-frame + action arrays, self-describing, detection-labels-later
**Decision:** The on-disk recording schema is locked as **v1** in `DATA_FORMAT.md` (Issue #5). One `.npz` per session: index-aligned per-frame arrays `frames` (N,150,270,3 uint8 BGR), `timestamps` (float64), `keys` (N,11 uint8), `lclick`, `rclick`, `dx`, `dy` (int32); plus metadata `key_names`, `schema_version`, `geom`, `loop_fps_target`. The FPV half stands.
**Why:** Everything downstream (loader #6, radar gate #7, detection #8–9, models) reads this, so it's locked now while fresh and before #4 hardens tooling around it. Key choices, each deliberate: (1) **store the full frame, not a radar crop** — keeps the radar recoverable for the #7 gate (cropping it away would make #7 impossible) and defers centre/radar sub-crops to the loader per D-012; the spec's "radar crop region" is intentionally NOT baked in because #7 hasn't yet proven the radar carries signal, and on-machine the 150x270 radar is region-level only. This is the schema D-012/D-015/D-016 imply, now made authoritative.

### D-016 · Recording loop bar set at 15 FPS (met); cost is entirely the mss grab, logging is free
**Decision:** The committed recording-loop rate bar is **sustained ≥ 15 FPS**. The earlier informal 20 FPS loop target is **retired deliberately** (not silently) as too high for the known capture cost. Measured recording rate is **~14.8–15 FPS**, so the bar is met. `LOOP_FPS` in `recorder.py` is set to 15 to match reality rather than target an unreachable 20. **Note (D-024):** the radar crop adds a small per-frame cost on top of the grab; `--profile` remeasures it, and the ≥15 bar still applies.
**Why:** `recorder.py --profile` broke the per-frame cost into stages on-machine (537 frames): frame grab **37.17 ms (100%)**; mouse read 0.01 ms; keys+clicks 0.04 ms; record assembly 0.02 ms. So the loop is entirely bounded by the mss grab+resize (the known-slow path, D-013/D-014) and our whole input-logging apparatus — raw mouse deltas, key/click reads, record building — adds ~0.07 ms, i.e. **free**. That's the key finding: #3 costs nothing on top of #2; the FPS is inherited capture cost, not sync overhead. Unpaced ceiling is ~27 FPS; paced-to-20 with a variable ~37 ms grab realises ~15 (the pacer can't reclaim time on overrunning grabs). The reference study's entire loop (capture + inference + output) ran at 16 FPS and worked, so ~15 for capture+logging — before models — is in proven-workable range. Setting the floor at 15 is honest; chasing 20+ would mean fighting the capture backend now, before we know the models' cost, which the derisking discipline says not to do. **Lever unchanged:** if the full agent loop (adding two-model inference) drops too low, swap mss -> dxcam (D-014); that's the documented escape hatch, a decision not a silent swap. **Minor note:** the pacer targeting a rate the grab can't sustain is slightly self-defeating (adds sleep on fast frames, can't compensate on slow ones); left as-is for now since the realised rate is acceptable and this is not worth the complexity mid-gate.

### D-015 · Aim is captured from raw mouse deltas; #3 is a single synchronous loop
**Decision:** Issue #3 records our own play with a **single synchronous loop** (grab frame + read keys/clicks + read accumulated raw mouse delta, one matched record per tick). Keyboard and mouse buttons are read via pywin32 `GetAsyncKeyState` (works during gameplay). Mouse *aim* is captured as **raw device deltas (dx, dy) via the Windows raw input API** (`src/raw_mouse.py`, WM_INPUT on a background message-only window), accumulated between frames and read once per frame. Files: `src/raw_mouse.py` (listener) and `src/recorder.py` (loop, with `--verify`/`--record`/`--dryrun`).
**Why:** The reference study got the player's aim from **view angles read out of game memory** (RAM offsets via pymem) — dead on Source 2 and excluded by D-002. Its `mouse_check()` read `GetCursorPos`, which is useless in CS2 because the game locks/hides the cursor during play (it would report a frozen point). Raw input reads deltas straight from the mouse *device*, independent of the OS cursor, so it keeps working under the in-game cursor lock — this is exactly why raw input is the standard path for FPS mouselook. **Two consequences recorded honestly:** (1) our aim signal is *relative motion per frame* (dx, dy), not the study's *absolute view angle* — a genuine difference in what the combat model learns from, accepted because it's the only self-recording-only path open to us. (2) Raw input emits one WM_INPUT per motion tick and a high-DPI/high-polling mouse can flood the queue and even tank game FPS under fast movement (measured phenomenon); so we deliberately do NOT process per event — the listener only ACCUMULATES dx/dy and the loop reads the sum per frame, which is both what the model needs and what avoids the flood. **Way-one (synchronous) over threading:** the gate's whole job is to *prove* input-at-frame-N matches screen-at-frame-N; the simplest loop is the one whose correctness is verifiable. Threading would buy sub-frame mouse resolution we can't use at ~20-25 FPS anyway, at the cost of the exact drift failure this gate exists to rule out. If aim later needs finer sampling, add it then, for a measured reason, on a proven-synced base. **Unverified as of writing:** like capture, none of this has been run here — the raw-input listener especially may need on-machine iteration (DPI, polling, focus, fullscreen). `raw_mouse.py --selftest` and `recorder.py --verify` exist precisely to prove it on-machine before real recording; `--verify` failing is a kill-flag condition per PROJECT_ISSUES #3, not a detail to wave through.

### D-014 · #2 capture rate bar set at 20 FPS (met); dxcam is the deferred lever if the full loop needs more
**Decision:** The committed "usable rate" bar for the #2 capture gate is **sustained ≥ 20 FPS**, measured by `--benchmark`. Current measured capture rate is **~25 FPS** (mss ~26 ms grab + cv2 ~14 ms resize per frame, 1920x1080 -> 150x270), so the bar is **met with margin**. We do NOT chase 30 FPS on capture-in-isolation. **dxcam** (Windows Desktop Duplication API) is recorded as the known faster-capture lever, deferred, to be pulled only if the *full agent loop* proves too slow.
**Why:** #2 is the easy gate; #3 (frame/input sync) is the hard one and the real M0 risk. Optimising capture alone past 30 spends effort on a number that model inference will later eat into anyway — the meaningful budget is the *whole loop* (capture + logging + two-model inference), which can't be measured until those exist. The reference study's entire loop ran at 16 FPS and produced a working agent, so ~25 FPS for capture alone is comfortably in proven-workable territory; 20 is set as the floor (just above the study's 16, with headroom) so normal drift or #3's logging overhead doesn't push us under our own bar for no real reason. Profiling (D-013) already showed both mss (~26 ms) and the resize (~14 ms) are slower than ideal on this hardware, consistent with a non-SIMD PyPI OpenCV build and mss's generic Windows copy path — both fixable, neither worth fixing now. **The lever, for a future session:** if the full loop is too slow, swap mss -> dxcam (typically several times faster for full-screen grabs, and hands back frames in a cheaper form). That would change D-010 (currently commits to mss) and needs its own calibration pass, so it is a decision, not a silent swap. Deferring it avoids over-investing in the easy gate and lets the real full-loop budget — measured later, not guessed — decide whether it's even needed.

### D-013 · Capture resize uses INTER_LINEAR, not INTER_AREA
**Decision:** The downscale in `capture.py`'s `grab()` uses `cv2.INTER_LINEAR`. Not `INTER_AREA`, despite AREA being the textbook choice for shrinking images. **Note (D-024):** this applies to the FPV downscale. The radar crop uses `INTER_AREA` deliberately — it's a small 128x128 target where AREA's averaging is cheap in absolute terms and quality matters more for reading position.
**Why:** Benchmarked on this machine (2026-08), `INTER_AREA` resizing 1920x1080 down to 270x150 cost ~24 ms/frame — roughly half the total per-frame budget and the single largest contributor to a sub-bar 20 FPS. At a ~7x per-axis reduction `INTER_AREA` averages over every source pixel in each output cell, which is expensive; `INTER_LINEAR` is far cheaper and on a 150x270 frame feeding a CNN the quality/anti-aliasing difference is negligible. This was found by adding a grab-vs-resize timing split to `--benchmark` after a raw 20 FPS reading, and it overturned the initial assumption that mss was the bottleneck — mss (~26 ms) and the resize (~24 ms) were near-equal, and the resize was the fixable half. **Note for a future session:** do not switch this back to `INTER_AREA` "for quality" without re-checking the FPS cost; the speed hit is real and was measured. If frame quality ever proves to matter for aim, revisit with a measurement, not a default.

### D-012 · Fullscreen 1920x1080 capture, full-frame crop, 16:9 model input (150x270)
**Decision:** CS2 is run **fullscreen at the monitor's native 1920x1080**. The capture crop is the **full frame** (LEFT=0, TOP=0, 1920x1080) — stored as an absolute monitor-relative rectangle in `src/capture_config.py`, separate from capture logic, confirmed via `python -m src.capture --calibrate`. The FPV model input size is changed from the study's 150x280 (~4:3) to **150x270 (H,W), which is 16:9**. Frames leave in BGR (Q4). **Note (D-024):** the full-frame grab is also what makes the high-res radar crop possible — the minimap exists at full resolution in the grab before the FPV downscale.
**Why:** Calibration killed the original plan of matching the study's 1024x768 *windowed* setup. On this machine the native monitor is 1920x1080 (16:9); the study's inward offsets (824x498) landed the crop in a corner and cut away most of the game. Running CS2 fullscreen at native res makes the full-monitor grab pure game edge to edge, so the crop is trivially full-frame — no window-position hunting, no desktop/taskbar to exclude. **The aspect consequence is the real content of this decision:** the source is now 16:9 but the study's 150x280 target is ~4:3, so a naive resize would horizontally distort every frame (a quiet quality bug, worst for aim precision). Changing the input to 150x270 (1920/1080=1.778; 150x270=1.80, ~1.2% off, both dims cleanly divisible for CNN pooling) makes 1920x1080 -> 150x270 a pure uniform downscale with no distortion. Exact parity with the study's 150x280 first-layer size is dropped deliberately — D-001 already says we don't run or compare against their model, so parity buys nothing while an undistorted frame at real resolution buys a lot. **Trades noted:** (1) fullscreen 1920x1080 departs from the study's 4:3 1024x768 (Q1), accepted for a clean undistorted capture; (2) full-frame keeps peripheral margins the study discarded to concentrate resolution on the centre — that centre-vs-edges trade is deferred to the per-model sub-crops in the loader (#6: full FPV / centre / radar), tuned against real data, not resolved at capture where keeping the whole frame protects the radar from being amputated. **Supersedes** the earlier 1024x768-windowed framing of Q1 for capture geometry; 150x270 is the value #5 (DATA_FORMAT.md) must lock authoritatively.

### D-011 · Python stack is native-Windows TF 2.10 + CUDA 11.2 + Py 3.10, with GPU on the RTX 4050
**Decision:** The environment is Python 3.10, TensorFlow 2.10.1, cudatoolkit 11.2, cudnn 8.1.0, numpy 1.26, plus mss / opencv-python / pillow / matplotlib, via conda (`environment.yml`). CUDA libs come from conda-forge; TF and the vision/capture pip deps are pip-installed into the conda env. Everything runs on native Windows. Supersedes D-009.
**Why:** The machine has an **RTX 4050** (Ada, compute capability 8.9). This one fact collapsed the earlier options: (1) D-009's TF 2.3 / CUDA 10.1 stack cannot see an Ada card at all — CUDA 10.1 tops out at Turing (CC 7.5) — so on this hardware D-009 was silently CPU-only. (2) "Modern TF on the GPU on native Windows" does not exist: **TF 2.10 was the last release with native-Windows GPU support**; from 2.11 GPU requires WSL2 or CPU-only. (3) WSL2 + modern TF would give newer TF but split the agent across two OSes — model in Linux, capture (#2) and input (#3) on Windows where CS2 runs — precisely at the capture+sync gate that is the project's #1 risk. So the stack that (a) uses the 4050 and (b) keeps the whole pipeline on one OS is **TF 2.10 native Windows**. Official pairing (per TF install guide): `cudatoolkit=11.2`, `cudnn=8.1.0`, Python 3.9–3.11; confirmed working on Ada with a current NVIDIA driver. Conda is still required because pip won't install CUDA libs on Windows. Parity with the reference's TF *version* is dropped — D-001 already says we don't run their agent or load their `.h5` weights, so version parity buys nothing, whereas a working GPU on the actual hardware buys a lot. **Trade accepted:** TF 2.10 is a 2022 release (not bleeding-edge), and the CUDA toolchain must match exactly or the GPU won't be detected — acceptable, since M2–M4 models are small and the real bottleneck is data, not FLOPs.

### D-010 · Capture library is `mss` full-screen grab + crop (win32 BitBlt is dead)
**Decision:** Screen capture uses `mss` to grab the full screen, then crops to the CS2 game region and resizes to the fixed model input. The reference study's `screen_input.py` win32 `BitBlt`/`GetWindowDC` path is not carried over.
**Why:** This was already the ground truth in PROJECT_ISSUES #2 but had no decision entry, so it kept living only in issue text. CS2 is Source 2; the legacy D3D9-era `BitBlt` capture the reference relied on is dead/unreliable on it. `mss` is already a dependency in the reference's own `e2e.yml` (7.0.1), so it carries over cleanly. Recording it here so it isn't re-litigated.

### D-009 · Python stack pinned as a faithful conda repro of the reference (TF 2.3 / Py 3.7)
**Status:** **SUPERSEDED by D-011 on 2026-08.** Reason: the target machine has an RTX 4050 (Ada, CC 8.9), which the CUDA 10.1 toolchain in this stack cannot address — making this stack CPU-only on the actual hardware. Replaced with a native-Windows TF 2.10 + CUDA 11.2 stack that uses the GPU. The entry is kept below for the decision trail.
**Decision:** The environment reproduces the reference study's `e2e.yml` stack — Python 3.7, TensorFlow 2.3, numpy 1.18, OpenCV 4.4, mss 7.0.1 — via conda (`environment.yml`), not via `pyproject.toml`/uv. The pieces tied to the reference's dead memory-inference and win32-capture paths (`pymem`, and the `BitBlt` use of `pywin32`) are dropped from the core; `pywin32` is kept only for simulated key output later.
**Why:** Chosen deliberately over a modern stack (see below) for exact parity with the reference methods. The originally-requested combination — TF 2.3 + Py 3.7 + pyproject/uv + a modern CUDA build — is not installable as a set: Py 3.7 is EOL and below uv/Poetry's floor; TF 2.3's only official GPU path is CUDA 10.1 + cuDNN 7.6, which installs via conda (not pip/uv) and does not target current NVIDIA cards (RTX 30/40/50). Conda is therefore mandatory for this stack, which is why the reference itself shipped a conda env. **GPU caveat:** the CUDA 10.1 GPU path works only on older GPUs; on current cards the env runs CPU-only until the stack is modernized. Reconsider (move to modern TF or PyTorch on Py 3.11) if the EOL interpreter or CPU-only training becomes a real blocker.

### D-008 · The agent maintains this log and the other living docs
**Decision:** Updating `DECISIONS.md`, `DATA_FORMAT.md`, and `PROJECT_ISSUES.md` is part of doing the work, not a separate chore. New decisions are appended here as/before they are acted on.
**Why:** The plan reversed direction several times during scoping (see below). Without a written record, each new session re-litigates settled questions and re-suggests rejected approaches. The log is the memory that prevents that.

### D-007 · Offline / local bot servers only
**Decision:** The agent runs only against local servers with bots, never online matchmaking.
**Why:** Simulated keyboard/mouse input and any memory reading can trip anti-cheat. Offline is also how the reference research ran. Safety + it matches our actual need.
**⚠ TENSION — RESOLVED by D-041 (2026-08):** this decision governs where the *agent* runs. Training *data* is recorded in online MM (D-035): capture + raw-mouse-hook + GSI-listener during live matches. That mismatch is now resolved in **D-041**: (1) MM recording is READ-ONLY and sanctioned (low risk — no injected input); (2) the agent still runs OFFLINE by default *now*; (3) online agent play is opened only as a FUTURE step at explicitly accepted VAC-ban risk (injecting simulated input into a VAC-protected match is what this rule was written to avoid). **So D-007's offline default still governs how the agent is run today** — the agent runs offline against local bots until a further explicit "go online" decision. See D-041 for the full resolution and the risk accepted.

### D-006 · One map end-to-end before multi-map
**Decision:** Nail a single map (Dust2) through the whole pipeline before authoring any others.
**Why:** Multi-map is a multiplier, not a prerequisite. Per-map panel authoring is real work; doing several before one works end-to-end is scope ahead of a working core.

### D-005 · The probability panel is hand-authored, not learned
**Decision:** Enemy-location-over-round-time priors are encoded as heuristics from CS knowledge, not learned from our dataset.
**Why:** Round-timing enemy priors are a competitive-play concept. Our self-recorded data is unstructured (deathmatch-style, no coordinated round timing), so the signal to learn them isn't in the data. Hand-authoring is legitimate and is the only viable path with our data.
**⚠ CORRECTION (D-035, 2026-08):** the "why" above is now known to rest on a FALSE premise. The data is NOT deathmatch-style — it is matchmaking (see D-035), which DOES have coordinated round timing. So the original justification ("the signal isn't in the data") no longer holds as stated. **The decision (hand-author the panel) is NOT overturned here** — it may still be the right call for other reasons: MM round-timing priors are subtle, our data volume is small (D-023 floor), enemy *positions* are observer-only in GSI (D-030) so per-round enemy-location ground truth still isn't directly recorded, and the panel being hand-authored keeps M5 simple. But the premise change means D-005 is now genuinely REOPENABLE: if/when there's enough MM data and a way to derive enemy-location signal, learning some priors instead of hand-authoring them becomes a real option worth weighing. Flagged, not decided — do not treat "panel is hand-authored" as resting on the deathmatch claim anymore.

### D-004 · Detection comes from the first-person image, never the radar
**Decision:** Enemy detection is done by the vision model on the FPV. The radar/panel is only for navigation and positioning.
**Why:** In CS2 the radar only shows enemies a teammate currently sees. A solo agent's radar shows essentially no enemies. Any design that expects the radar to reveal enemies is broken. This also cleanly separates the two feeds: radar → "where am I / where should I be," vision → "is someone actually there."

### D-003 · Detection labels are a separate data problem; action labels are free
**Decision:** Treat enemy-detection label creation as its own milestone with its own method and risk. Do not assume it comes from recording.
**Why:** Self-recording logs our own inputs automatically (action labels free), but tells us nothing about where enemies are on screen. Detection labels require their own creation method (annotation or an automated ground-truth source). This is the most underestimated part of the data work.

### D-002 · Self-recording is the spine; spectating is optional and late
**Decision:** Build the dataset by recording our own play. Spectating (recovering another player's actions) is a stretch track that must never block the critical path.
**Why:** Self-recording gives us our own actions for free — no inference needed. Spectating requires recovering a *stranger's* actions, which on CS2 means rebuilding the memory-inference pipeline the reference study did with RAM offsets + GSI — all dead on Source 2. That rebuild is plausibly larger than the rest of the project combined. It is quarantined as optional so it can't sink the timeline.

### D-001 · Build our own project and dataset; do not run or compare against the reference study
**Decision:** We build on the reference study's methods and findings, but train our own models on our own CS2 data. We do not use its dataset, run its agent, or benchmark against it. All success criteria are absolute bars we set for ourselves.
**Why:** Our architecture (two-feed panel + arbiter) and scope differ from the reference study's single end-to-end model. Reproducing or comparing against it would pull in dead dependencies (its CSGO-era capture, RAM offsets, GSI) and a comparison that doesn't map cleanly onto a different design. Training our own keeps scope focused on our actual research question. Superseded the earlier idea of reusing the study's dataset.
